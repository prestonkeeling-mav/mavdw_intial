Standard Definition

LookML View Standards

Purpose

This standard defines how BI Team LookML views should be named, documented, modeled, reviewed, and approved before they are treated as production-ready.

Naming

  • All LookML identifiers must use lowercase snake case.
  • This applies to view names, model names, Explore names, dimension names, measure names, join names, filter names, and parameter names.
  • Measure names should follow the pattern aggregation_type_dimension_aggregated.
  • Use total_ instead of sum_.
  • Avoid abbreviations unless they are widely understood and consistently used by the business.
  • If an abbreviation is used in a user-facing label, the description must define the full meaning.

Examples:

measure: total_sales {
  type: sum
  sql: ${sales_amount} ;;
}

measure: count_distinct_customers {
  type: count_distinct
  sql: ${customer_id} ;;
}

View Documentation and Grain

  • Every view must document its business purpose, physical source table or derived-table source, grain, primary key, known limitations, refresh expectations, data owner, and security classification where applicable.
  • Grain must clearly state what one row represents.
  • Known limitations should be explicit enough that reviewers and future developers understand where the view should not be used.

Example:

# Purpose: Supports daily item-level sales and profitability reporting
# Source: EDW.Maverik.COMBINED_ITEM_SALES_FACT
# Grain: One row per calendar key, organization key, and product key
# Primary Key: calendar_organization_product_key
# Refresh: Daily
# Data Owner: Business Intelligence
# Security Classification: Internal, no direct PII

Primary Keys

  • Every view must have a valid primary key.
  • The primary key must be unique at the documented grain, non-null, marked with primary_key: yes.
  • Composite primary keys may be used when the source table does not contain a single primary-key column.
  • Composite keys should be created upstream in the data warehouse whenever practical.

Dimensions and Measures

  • Every dimension and measure must have a meaningful description.
  • Descriptions must explain the business meaning, source column or fields, calculation, valid grain, exclusions, limitations, and assumptions where relevant.
  • Descriptions should explain the field, not merely restate the field name.
  • Calculated fields must describe the calculation in business-readable language.
  • All dimensions and measures should be mutually exclusive. No two dimensions should yield the same result, and no two measures should yield the same result.

Drill Fields

  • Default drill fields must be defined.
  • Drill fields should use the most granular human-readable information available for the underlying data.
  • Drills should include key identifying dimensions and the most important measures from the view.

Group Labels and Visibility

  • Any view with more than four dimensions or measures should use group labels.
  • Yes/no dimensions and one/zero flag fields should be placed in Flags & Filters, or a clearly modified version such as Transaction Flags & Filters.
  • Primary keys, foreign keys, and related identifiers should be placed in Keys & IDs.
  • Fields should be hidden only for a documented reason, such as technical join keys, deprecated fields, restricted fields, or fields that could cause misinterpretation.
  • Fields must not be hidden merely to make an Explore look cleaner.

Dimension Groups

  • Date and timestamp fields should generally be modeled as dimension groups.
  • Every dimension group must explicitly define its available timeframes.
  • Choose timeframes intentionally for the expected business use.
  • Avoid ambiguous names such as date, month, and year; prefer event-specific names such as transaction_date, invoice_date, posted_date, or delivery_date.

Measure Logic

  • Measures should use native Looker measure types whenever practical.
  • Measures should reference existing LookML dimensions rather than repeating source SQL.
  • Measure names and descriptions must make clear whether the measure is a row count, distinct business-entity count, total, ratio, weighted value, period-ending balance, or snapshot value.
  • Measures that use division must use NULLIF to protect against divide-by-zero errors.
  • Ratios should generally be calculated from aggregated numerators and denominators.
  • Do not average row-level percentages unless there is a documented business reason.
  • Distinct measures must document why distinctness is required, what entity is counted, which field defines distinctness, and whether the result changes at different grains.
  • Do not use Looker's average measure type. Averages must be defined as an aggregate divided by the count of a specific business unit.
  • Measure names must identify what is being averaged, such as average_daily_sales, average_units_per_transaction, or average_labor_hours_per_week.
  • Every measure must use an appropriate format for dollars, precision-sensitive amounts, ratios, counts, gallons, units, hours, or other business units.

Labels and Canonical Definitions

  • User-facing labels must be written for business users.
  • Labels should use Title Case, avoid technical database terminology, avoid unnecessary table or source-system names, include units when needed, differentiate similar fields, and match established business terminology.
  • Similar concepts must either be consolidated or clearly differentiated by source, grain, timing, scope, calculation, or included activity.
  • Business attributes should be defined once in their canonical reference view.
  • Fact views may define foreign keys, transaction-specific attributes, and fields genuinely part of the fact-table grain.
  • Fact views should not duplicate descriptive attributes owned by reference views.
  • Fields that require other fields for links or display behavior must document that requirement and use group_item_label where appropriate.

Security

  • If a view or field contains PII or restricted data, access must be restricted with proper Looker security controls.
  • Hiding a field is not an acceptable security control by itself.
  • Escalate PII or restricted-data handling to the BI Manager until a separate PII standard exists.

Approval

  • A developer may not approve their own pull request.

Any BI Team Member may review the following:

  • Changes to existing measures
  • Changes to dimensions that are not used in joins

Changes Requiring BI Manager Approval:

  • New Views
  • Changes to dimensions used in joins
  • Changes to views containing PII
  • Where a view explicitly requires BI Manager Approval.

Review Checklist

  • [ ] View name uses lowercase snake case.
  • [ ] View purpose is documented.
  • [ ] Source table or derived source is documented.
  • [ ] Grain is documented.
  • [ ] A valid primary key is defined.
  • [ ] Primary key is expected to be unique at the documented grain.
  • [ ] Every dimension has a meaningful description.
  • [ ] Every measure has a meaningful description.
  • [ ] Dimensions and measures are mutually exclusive.
  • [ ] Group labels are used where appropriate.
  • [ ] Hidden fields have a documented reason.
  • [ ] User-facing labels use business terminology.
  • [ ] Similar fields are clearly differentiated.
  • [ ] Canonical reference attributes are not duplicated.
  • [ ] Measures use appropriate formats.
  • [ ] Division uses NULLIF.
  • [ ] Ratios use aggregated numerators and denominators.
  • [ ] No Looker average measures are used.
  • [ ] Average calculations identify the specific denominator.
  • [ ] Drill fields identify the underlying row or business event at the lowest useful grain.
  • [ ] PII is identified and restricted.
  • [ ] Reviewer approval level matches the change type.
  • [ ] BI Manager approval is present when required.

Notes

Use this standard when creating, changing, or reviewing LookML views. A view should not be considered production-ready until its grain, primary key, field descriptions, measure behavior, labels, drill behavior, security handling, and validation evidence are clear enough for another BI Team member to review without undocumented context.
