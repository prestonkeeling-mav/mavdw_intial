Standard Definition

LookML Explore Standards

Purpose

This standard defines how BI Team LookML Explores should be named, grouped, joined, validated, secured, reviewed, and approved before they are treated as production-ready.

Naming

  • All LookML identifiers must use lowercase snake case.
  • This applies to view names, model names, Explore names, dimension names, measure names, join names, filter names, and parameter names.
  • Avoid abbreviations unless they are widely understood and consistently used by the business.
  • If an abbreviation is used in a user-facing label, the description must define the full meaning.

Explore Group Labels

Every Explore must have a group label. The group label must use an approved value. New group labels require BI Manager approval.

Approved group labels:

  • Frequently Used Explores
  • External Data From Business Partners
  • KPS - Information
  • Kum & Go Legacy Databases
  • Landing Zone
  • Payment Partner Information
  • Paytronix Information
  • PDI Company - Combined
  • PDI Focal Point - Maverik
  • People Data
  • Reference Information
  • Schematics
  • Summary Information - Ridgeline
  • Summary Information - Database
  • Summary Information - Transactions
  • UKG Dimensions

Explore Descriptions

  • Every Explore must have a description.
  • At minimum, the description must explain what business questions the Explore is intended to answer.
  • Descriptions should be specific enough that a user can determine whether the Explore is appropriate before opening it.

Example:

explore: item_profitability {
  description: "Analyze item-level sales, cost, waste, and profitability by site and fiscal period."
}

Explore Approval

Require BI Team Member Approval:

  • Non-security changes/additions to existing Explores

Require BI Manager Approval:

  • New Explores
  • Security Permission Changes
  • Many-to-many joins

Base View and Grain

  • The base table or base view of an Explore should be the most granular table used by the Explore.
  • Developers must document the base-view grain and understand how each join changes or preserves that grain.

Required Reference Views

  • Reference views needed for users to identify, filter, or group the base data should be included.
  • If base data contains important date fields, join the day-level and month-level calendar information views.
  • If the dataset contains Site ID or Organization Key, the organization view should normally be included.
  • If the dataset contains an identifier users need to understand, the associated reference view should normally be joined.
  • Reference views should provide human-readable descriptions and relevant hierarchy fields.

Join Standards

  • Every join must explicitly define its relationship.
  • Join fields should use persisted columns, compatible data types, the same business concept, and avoid unnecessary transformations.
  • Join conditions should not normally include casts, concatenation, date transformations, string manipulation, functions, formulas, or OR conditions.
  • If a formula or transformation is unavoidable, it must be documented and approved; the logic should preferably move upstream into the warehouse or governed transformation layer.
  • Join logic must not silently remove base-view records without clear documentation.
  • When the same view is joined multiple times, each join must have an appropriate user-facing view label that clearly explains the role the joined view serves in the Explore.

Example:

join: organization {
  type: left_outer
  relationship: many_to_one
  sql_on: ${sales.organization_key} = ${organization.organization_key} ;;
}

Explore Validation

Validate on every change:

  • For existing Explores, compare key measure totals with and without all joined views before and after the change.
  • Run a query from the base view with one representative column from each joined view. It should run in less than 10 seconds or no slower than before the change.

Validate on new explores and major changes:

  • Execute 100 representative query runs and confirm it runs in less than 10 seconds.
  • Validate that existing dashboards using this Explore still function as before. If multiple dashboards use the Explore, validate the top three by usage.
  • Performance exceptions require BI Manager approval and must be documented with the expected performance and business justification.

Security

PII and security-permission handling are out of scope for this standard until a separate PII standard exists. Security permission changes require BI Manager approval.

Review Checklist

  • [ ] Explore name uses lowercase snake case.
  • [ ] Explore group label uses an approved value.
  • [ ] Explore description explains the business questions it answers.
  • [ ] Non-security changes/additions to existing Explores have BI Team Member approval.
  • [ ] New Explores have BI Manager approval.
  • [ ] Security permission changes have BI Manager approval.
  • [ ] Many-to-many joins have BI Manager approval.
  • [ ] The base table is the most granular table in the Explore.
  • [ ] Required reference views are included.
  • [ ] Join relationships are explicitly defined.
  • [ ] Join cardinality has been validated.
  • [ ] Join fields use compatible data types.
  • [ ] Join conditions avoid formulas and transformations.
  • [ ] Multiple uses of the same view have clear view labels.
  • [ ] Existing Explores compare key measure totals with and without all joined views before and after the change.
  • [ ] A query from the base view with one representative column from each joined view runs in less than 10 seconds or no slower than before the change.
  • [ ] LookML Validator passes.
  • [ ] Content Validator passes.
  • [ ] SQL validation passes.
  • [ ] For new Explores and major changes, 100 representative query runs average less than 10 seconds.
  • [ ] For new Explores and major changes, existing dashboards using the Explore still function as before, including the top three by usage when multiple dashboards use the Explore.
  • [ ] User-facing field names match established business terminology.

Notes

Use this standard when creating, expanding, or reviewing LookML Explores. A production-ready Explore must have a clear business purpose, approved group label, appropriate base grain, validated joins, documented security handling, representative validation evidence, and performance testing appropriate for normal business use.
